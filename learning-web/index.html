📖 从完整 Agent 流程学习 Day 2

我们不是为了记 Python 语法而做工单模型。Pydantic 是 AI 输出到企业业务操作之间的一道可执行数据契约。先看模型在整个 Agent 系统中的位置。

用户提出工单 → FastAPI 接收与验证
    → 知识库检索 RAG（提供来源）
    → LLM 生成建议（不直接执行）
    → Pydantic 验证 AI 输出格式
    → 策略引擎检查权限与风险
    → 需要时人工审批
    → 调用 CRM / Salesforce 工具
    → 审计日志 + 质量评估
今天真正做的是第 1 步的输入校验和第 4 步的结构化输出校验。校验通过 ≠ 内容真实 ≠ 获得执行权限。 这三件事必须分开设计。

工单场景：哪些字段谁来提供？

客户报告“決済画面でエラー”。客户提供 subject 和 description；系统生成 id、created_at、初始 status；AI 只能建议类别、优先级、摘要和是否要求人工确认。

练习会用到的语法（不再突然考试）

1. BaseModel、类型注解、必填与默认值

from pydantic import BaseModel

class Customer(BaseModel):
    name: str          # 必填字符串
    locale: str = "ja" # 省略时默认 ja

Customer(name="田中")

class 定义模型；: 后面是预期类型；有 = "ja" 就有默认值。普通 Python 类型注解本身不会自动进行运行时验证，Pydantic 在实例化时才执行规则。

官方文档：BaseModel、字段定义与必填

2. Field：类型在冒号后，限制在等号后

from pydantic import Field

subject: str = Field(min_length=3, max_length=120)
summary: str = Field(min_length=5, max_length=300)

str 是类型，Field(...) 是验证规则。不要写 summary: Field(...)，因为 Field 不是类型。ge/le 用于数字，min_length/max_length 用于文本等长度。

官方文档：Field 参数与验证约束

3. ConfigDict：拒绝未知输入字段

from pydantic import ConfigDict

class TicketCreate(BaseModel):
    model_config = ConfigDict(extra="forbid")
    subject: str

extra="forbid" 会拒绝客户偷偷多传的字段，避免无意间信任客户端提供的系统属性。如果什么都不设，Pydantic 默认可能忽略未知字段。

官方文档：ConfigDict / extra

4. 继承、UUID 和 datetime：系统字段

from uuid import UUID
from datetime import datetime
from typing import Literal

class Ticket(TicketCreate):
    id: UUID
    created_at: datetime
    status: Literal["new", "triaged"] = "new"

Ticket(TicketCreate) 继承输入字段。UUID 表示标识符格式，datetime 表示日期时间；标注不会自行生成值，必须由服务层生成。Literal 把状态限定为列举值。

Python 文档：Literal · UUID · datetime

5. StrictBool：AI 输出必须是明确的布尔值

from pydantic import StrictBool

class ApprovalDecision(BaseModel):
    needs_human_review: StrictBool

普通 bool 可能接受字符串 "yes" 并转换为 True；StrictBool 拒绝这样的隐式转换。即使是合法的 True / False，AI 也没有获得执行 CRM 写入操作的权限。

官方文档：StrictBool

6. 测试与排错：看异常，不猜答案

from pydantic import ValidationError
try:
    TicketCreate(subject="NG", description="内容不足")
except ValidationError as exc:
    print(exc.errors())

语法错误（如缩进）发生在 Python 解析阶段；模型规则错误会在 Pydantic 验证阶段产生 ValidationError；依赖下载失败则是运行环境错误。三者不是一回事。

开始写题前，应该能在上面找到每种语法的例子和官方出处。网页内的10项检查使用真正的 Python/Pydantic；首次载入需要网络，后续在同一页面中复用运行器。

第三关完整题目：TriageResult 是 AI 的“工单分析结果”

先理解业务：客户提交工单后，AI 会提出问题分类、处理优先级和简要摘要。今天不实现自动分类算法，不编写 Prompt，也不调用 LLM。你只需要声明允许的输出字段、类型与规则，由 Pydantic 拒绝非法结构。

示例：客户到底遇到了什么问题？

客户输入：
クレジットカードで決済しようとすると
エラーが発生し、注文を完了できません。

未来的 Agent 可以建议下面的分析结果，前提是基于实际业务规则与证据；这里的优先级只是为了讲解的示例，不是自动判级规则。

{
  "category": "payment_issue",
  "priority": "high",
  "summary": "決済時にエラーが発生し、注文を完了できない",
  "needs_human_review": true
}

这四个字段各自代表什么？

category = 问题类别：客户遇到了哪种业务问题？本题可选 payment_issue（支付）、access_issue（登录/访问）、general（一般咨询）、other（其他）。用 Literal 定义允许值，不能随意添加字符串。

priority = 工单处理优先级：排队处理时的重要或紧急程度。本题可选 low（低）、medium（中）、high（高）、critical（严重）。今天只限制允许值；如何判级是未来策略与模型设计的任务。

summary = 客户问题的简短摘要：例如“決済時にエラーが発生し、注文を完了できない”。必须是5～300字符的字符串，不是固定枚举；用 str = Field(min_length=5, max_length=300) 约束。摘要本身是否准确，还要未来单独评估。

needs_human_review = 是否需要人工复核：必须是 True 或 False；字符串 "yes" 无效，使用 StrictBool。这个标记是复核建议，不意味着模型已获准修改 CRM。

你要写的代码与通关条件

请在 class TriageResult(BaseModel) 内定义上述4个必填字段；使用 Literal 限制 category / priority，使用 Field 限制 summary，使用 StrictBool 约束人工复核标记。

正常样例应当成功创建模型；当 priority="super_urgent"、summary="NG" 或 needs_human_review="yes" 时，必须报验证错误。你不需要判断这条客户工单究竟应当选 high 还是 medium。

不懂语法时先查：Pydantic Field · Literal · StrictBool
